# FlowStudio Lite

A lean, ZDola-style desktop app for **Google Flow**: add your Google accounts once, paste a list of prompts, press **Generate** — the app rotates accounts automatically when credits run out and downloads the finished videos, in prompt order, to a folder you choose.

Built as a clean rewrite of FlowStudio V2, keeping its proven Google Flow page automation while fixing the audited high-severity problems (see "What was fixed vs V2" below).

## Install (Windows PC)

1. Install **Node.js 18+** (https://nodejs.org) and **Google Chrome**.
2. Unzip `flowstudio-lite.zip` anywhere, e.g. `C:\FlowStudioLite`.
3. Open a terminal in that folder and run:

   ```
   npm install
   ```

   (This installs Electron + the two runtime libraries. First run may take a few minutes.)
4. Start the app with **`start_flow_studio_lite.bat`** (double-click), or `npm start`.

Your data lives next to the app: accounts database in `data\`, one Chrome profile per account in `profiles\<account-id>\`, saved per-account cookies in `data\cookies\` (v2.0.0), downloaded videos in the folder you pick on the Generate page (default: `Downloads\FlowStudioLite_Videos`).

## How to add accounts

**Option A — Sign in once (recommended)**
1. Sidebar ke **Accounts box** me **+ Add Account** dabao — just type a name (the email field is optional, only a memory aid) and press **Add Karo**. The account exists immediately; nothing else is asked.
2. On the new card click **Sign In** (once signed in, this button reads **Chrome ↗** — it opens that account's own Chrome whenever you want to look). A normal Chrome window opens on Google Flow using that account's own dedicated profile.
3. Log in to Google normally (password / phone prompt as usual). The app detects the login from the profile, saves the email, and syncs the real credit balance when you close the window.
4. Done — the session is saved forever in that profile. Repeat for every account (unlimited).

**Option C — Add from cookies (v2.0.0; paste added v2.2.0)**
- If you have cookies for your Google accounts — a Netscape **cookies.txt** or a JSON export (EditThisCookie style) — sidebar ke Accounts box ke **🍪 Cookies se Add** button se: one modal, two big options — **📋 Cookies Paste Karo** (paste the cookie text straight in; a bad paste shows its error inside the modal and creates nothing) or **📁 Cookie File Chuno** (one file, or many at once via the **📥 Import** tab's bulk button — each file becomes one account; files are processed one at a time).
- The Google cookies (google.com / labs.google domains only) are injected into the account's own dedicated Chrome profile, and an **automatic check** runs immediately — the same live Flow check a Sync runs. The account is marked **Ready** only when Google Flow actually opens with the session.
- **Saved cookies + status chip (new in v2.0.0):** the parsed cookies are also **saved in the app's data folder, one file per account** (`data\cookies\<account-id>.json`), so the card's **🍪 Re-check** button can re-run the check later without the original file. Cookie values are never logged, printed, or shown anywhere. Each card shows a live **🍪 indicator chip**: **Checking…** while the automatic check runs, then **Live** (session works), **Ready** (works, credits low), or **Fail — \<reason\>** (dead/expired cookie, Google rejected the session, profile busy, network). The chip tells the truth: Google's device-bound sessions (DBSC) mean cookies copied from another device are often rejected — when that happens the chip honestly says Fail with the reason; it never shows a fake Live. **Sign In** and **profile import** always work regardless.

**Option B — Import from your installed Chrome**
- If you are already signed in to Google inside your regular Chrome profiles, use the **📥 Import** tab: **Import from installed Chrome** per profile, or *Import All*. The session files are copied into dedicated Lite profiles. If Windows reports the cookies were locked, close that Chrome profile first and import again.
- After importing, click **Sync** on each card to read its live Flow credit balance.

Each card shows: name/email, live credits, status (`Ready`, `LowCredits`, `Exhausted`, `Need Login`, `Cooldown`), a **Sync** button (re-reads the real balance from Flow), **Chrome ↗** (opens that account's own browser — the Sign In window for a logged-out account), and **Remove**.

Generation still needs the real profile free and will say so if it isn't.
>
> **v1.7.0 — the full self-audit: mismatch, save and credits edition.** The owner ordered a complete check on our own machine, and the audit (plus a new replica harness that drives the real engine against a fake Flow grid in a real Chromium — `tests/replica.js`) found and fixed FOUR live defects behind the persistent "download/prompt mismatch" reports: (1) the media-URL extraction read tiles from a BROADER selector list than the list its index was computed in, so the index landed on a neighbour's tile and the neighbour's fresh URL passed the identity gate — every tile lookup now goes through ONE canonical list, fingerprint-first (`_resolveTileIndexForTask`), for extraction, native download and retry alike; (2) submit-time "birth binding" was text-blind — in a burst, a task could lock onto a SIBLING's tile for the whole run; binding is now scored (and the score itself was fixed: containment instead of tile-side precision, because Flow expands short prompts into longer titles — the harness caught a prompt failing to match its OWN tile at 0.57 vs the 0.6 bar); (3) saves could silently overwrite a previous run's same-named video, and the native-download poll watched the shared download folder where another worker's save could be grabbed and renamed — saves now take a suffixed name instead of overwriting foreign files, and the poll watches only the session folder and only accepts files newer than the download click; (4) the Omni Flash credit table over-charged the local ledger ~40% (10 for a 6s clip) on every estimated deduction — text-to-video Omni is 1 credit/second, verified live (4s = 4 credits); Ingredients/Frames keep the older conservative estimates. Also: the unusual-activity auto-retry no longer falls back to clicking "the first button on the tile" — only a clearly-labelled retry button is ever clicked.
>
> **v1.6.2 — duration (and friends) now land where you set them.** Owner's report: the app had 6s selected, Flow generated at 8s. Audit of the settings sync found the cause: the controls were applied in the order ratio → duration → outputs → MODEL, and switching the model makes Flow reset the duration to that model's default — so the 6s click was silently overwritten to 8s by the later model switch, while the old verification only checked the pill wasn't in Image mode and cheerfully logged "synchronized & verified". Fixes: the model is now applied FIRST among the value controls; every control now binds to the VISIBLE settings popover (the old code used the first overlay pane in the DOM, which can be a hidden leftover); and after applying, the selected duration is READ BACK from the popover and repaired (up to 2 re-clicks) with the confirmed value logged — a click is never trusted on its own again.
>
> **v1.6.1 — never get stuck in Flow's editor.** Downloading clicks a tile open into Flow's video EDITOR; the old "return" was one Escape press plus a hunt for a Back/Done button by aria-label only, and when it missed, the page stayed in the editor — where the render monitor sees an empty grid, so the second video could neither finish nor download and the app sat on the editor screen until the render timeout (owner's photo: 2 generated, 1 downloaded, stuck). The return is now a verified escalation (history back → Done/Back by text or aria → direct project-URL navigation) that only reports success when grid tiles are actually present; the monitor also self-heals — an empty canvas on an /edit/ page sends it back to the grid and re-reads instead of idling; and the editor's download-button search now allows ~10s for the toolbar to paint.
>
> **v1.6.0 — the indifference rule, everywhere.** The owner's standing order: "agar koi open hai to us ka isme koi farak nahi pada, aur ye barabar chalta rahe" — if anything is open, it must make no difference; the tool just keeps working. v1.5.1 applied that to generation only, but Sign In could still refuse because a Sign In window was already open (possibly hidden behind the app), and Sync could still die against the open login window. Now EVERY app flow — Sign In, Sync / "I've logged in — Done", and Generate — reclaims the app's own login windows and credit checks and proceeds: pressing Sign In with a window already open simply closes the old one and opens a fresh one in front of you. The only remaining block is a video actually generating on that profile (two live Flow sessions in one profile would corrupt each other). One subtlety this required: a window closed by a reclaim no longer triggers the post-close auto-sync (its registration is removed at kill time, and the close handler checks it), so a reclaimed window can never kill its own replacement.
>
> **v1.5.1 — generation outranks credit checks too.** A live test showed Generate stopping with "(PID …, check)": at the moment Generate was pressed, the app's own invisible credit-check browser was mid-check on that account, and v1.4.1 treated any registered check inside its time budget as untouchable — so both prompts failed for a 30-second overlap. A credit check is disposable work; it must never block a generation. Now generation reclaims login windows AND running checks alike; only another live generation on the same profile remains protected.
>
> **v1.5.0 — the multi-video fix.** One video always worked; several prompts in one run produced errors and crossed wires. Deep audit found the cause in how finished renders were matched back to prompts: tiles were tracked by their position number in the grid (which shifts every time a new tile arrives), a tile could be claimed on just two shared words ("the", "and" counted), old tiles from earlier sessions became claimable again once the grid grew, and a prompt containing words like "blocked" or "failed" could mark its OWN tile as a policy failure. Now every task is bound to its tile by a stable fingerprint (the tile's prompt label) the moment it is submitted; claims need a strong, distinctive match; pre-existing tiles can never be claimed; failure detection reads only the tile's non-prompt text; and failed tasks release their claim so siblings are never starved. All matching logic is unit-tested (42 checks).
>
> **v1.4.1 — generation outranks the app's own Sign In window.** The v1.4 audit build correctly identified app-owned Chrome, but still treated the app's own open Sign In window (or a still-running credit check) as untouchable, so Generate could stop with "is account par abhi ek aur kaam chal raha hai". Now: pressing Generate closes the app's own Sign In window on that account automatically and carries on (your login stays saved in the profile); a credit check that hangs past 3 minutes is recognised as stuck and cleared; and every "busy" message now names the holding process (PID + kind), so nothing is a mystery anymore.
>
> **v1.4 — deep-audit fix for the invisible Chrome that held profiles hostage.** A full line-by-line audit found the real blocker: the app's own Sign In Chrome (opened before v1.3 existed) keeps running invisibly in Chrome background mode after its window closes, holding the profile and its cookie store — and every safeguard mistook it for your personal Chrome. v1.4 fixes this by ownership: any Chrome using one of this app's own profile folders was launched by this app, so if it is not a browser the app is actively using right now, the app closes it automatically and carries on (you will see a log line naming the PID it cleared). Your personal Chrome — different folders entirely — is never touched. Sign In, Sync and Generate all use this rule, and closing the app now also closes its Sign In windows instead of leaving them behind.

> Credit rules that protect your balances: a balance is only ever set to 0 when Flow itself reports 0 or shows its out-of-credits banner. An account that merely has *too few* credits for the selected model is marked **LowCredits** with its real balance intact. If a sync can't confirm the login state, nothing changes — only an actual Google sign-in redirect marks an account **Need Login** (and even then the last known balance is kept).

## How generation & rotation work

1. **Generate** page: paste prompts in **Paragraph mode** (one prompt per paragraph, blank line = new prompt — multi-line storyboards stay whole) or switch to **Bulk mode** (v2.0.0: **one line = one prompt** — paste a list of 50–100 prompts, or import a **.txt file** with the 📄 button; the whole list becomes the queue, each with its own status).
2. Pick **Model** (Omni Flash / Veo 3.1 Fast / Veo 3.1 Lite / Veo 3.1 Quality), **Duration** (4s–10s), **Aspect** (9:16 / 16:9 / 1:1), **Outputs** (x1–x4), **Ek saath kitne accounts chalein** (1–5 parallel accounts, default 3 — never more than this at once), and the **output folder**. Leave **Browser chhupa kar chalao (Background)** ON unless you want to watch the browsers work.
3. Press **Generate**. For each worker the app binds one account, opens Flow (in the background by default — no windows appear), applies the settings, and submits prompts in a burst window (up to 4 rendering at once per worker). To watch a specific account mid-run, press its card's **Chrome ↗**.
4. **Rotation:** when an account runs out of credits (or has too few for the chosen model), its unsubmitted prompts go back to the front of the queue and are picked up by the next account automatically. Prompts already rendering finish downloading first — a rotation never strands an in-flight video.
5. **Downloads:** each finished video is saved in prompt order as `scene001.mp4`, `scene002.mp4`, … in your output folder. A prompt only ever completes with **its own** video: the downloader uses the exact grid tile claimed for that prompt and that tile's own video stream. If a prompt's video can't be identified with certainty, the prompt is marked **Failed** with the reason (and a **Retry** button) instead of ever saving another prompt's video under its name.
6. **Stuck-render recovery (v2.1.0):** a prompt that was submitted (credits charged) but whose render tile is slow to appear is **never failed early**. The monitor keeps waiting (base wait raised to 10 minutes), periodically sweeps the project grid (scrolling so virtualized tiles mount) and fingerprint-scans for the tile, logging progress as it goes; the moment the tile appears, that same video is downloaded. Only after a full 10-minute in-project recovery search finds nothing is the task failed — with a reason that says so. A rotation or drain never abandons an in-flight render.
7. **Failover (v2.0.0; v2.1.0 single-account fix):** when a task fails on an account — credits out, need-login, cooldown, a Flow generation/render/download error — it **moves by itself to the next eligible account** and tries again there (**max 3 account tries** per task, then it fails visibly). **If NO other eligible account exists** (e.g. you run a single account), the task now **retries on the SAME account after a 60-second backoff** — as long as that account is still Live with credits left (max 3 submissions per account) — instead of dying with "(no usable account remained)". A safety/policy rejection never moves and never retries (the same prompt would be rejected everywhere). Each account's credits are only ever charged and recorded against that account. Every failover and same-account retry is written to the **Activity** page with its full detail.
8. **Pause / Resume / Stop** are at the top of the Generate page. If the app is closed or crashes mid-run, nothing is ever stuck on "running": on the next launch, in-flight tasks come back as pending — tasks whose prompt had already been submitted are flagged for **check-only recovery** (verified in the Flow project first, so a paid render is downloaded, never blindly re-submitted). Pressing **Stop** mid-run does the same for the tasks that had fired.

The **History** page (v2.2.0) is a table of every completed and failed task — video name, output folder, size, date, status chip — with search, All/Done/Failed + folder filters, **▶ Preview** (v2.0.0: plays the video **inside the app** in its own small window — no browser, no file manager), Retry on failed rows, multi-select with a bulk bar (**Delete Selected** removes file + record, always after a confirm; **Clear History** removes records only). The sidebar's **Accounts box** carries the credits picture (a one-line stats strip: total credits, live accounts, today's estimated spend, today's videos — plus the big TOTAL CREDITS at the sidebar's foot) and a **⚠ Low credits** badge on any account under 10 credits; the once-a-day low-credit alert lands in Activity. The **Activity** page records every major event — sign-ins, verify results, credit changes, generation start/done/fail, downloads, cooldowns, failovers, queue resumes, cookie checks — survives restarts (latest 500), filters by Generation / Credits / Login / Errors, and (v2.2.0) reads as a clean log-stream with a **Simple/Details** toggle and **Copy Log / Clear** controls.

1. **Backend capture saw nothing — and now it reports on itself.** All run long, the network layer registered **zero** media URLs (`mediaUrlsSeen = 0`): not one bound, not one even *seen*. The likely mechanism is the one disclosed in v2.8.0 — Flow's media arrives inside long-lived streaming/webchannel responses whose bodies Puppeteer only exposes when they *close* — but "likely" is no longer where it ends: the capture layer now **counts every response (armed or not), counts media responses separately, and records host names only** (never URLs/queries). ## What's new in v2.8.0 — downloads come from the backend now, not from buttons

The owner's direction after v2.7.0's PC test (the 4 UI/DOM strategies failed again on his machine): *"video banta hi backend sa direct fetch karaka download ka la"* — fetch the video straight from the backend the moment it is made. Before building, the real flow.google.com was inspected in depth (findings: `FLOW-INSPECTION.md`, verified from the live page + its JS bundle + a signed-in project): the API host is **aisandbox-pa.googleapis.com** (gRPC-style; generation is the *streaming* call `FlowService.StreamGenerateContent`), every generation's identity is its **workflowId**, and media is served as **FIFE URLs on `*.googleusercontent.com`** — usually with **no .mp4 extension**, signed and quick to expire.

1. **NEW — Network Capture Layer (`engine/networkCapture.js`).** Every worker page gets network listeners at launch (nothing can be missed), and ingestion arms at the exact moment a submission fires (`beginSubmission`). It watches all responses: `video/*` response URLs, and — most importantly — the API hosts' bodies, scanned **both** as JSON (deep-walk: a media URL is recognised by its host/shape under ANY field name) **and** as raw text (grpc-web binary frames can carry URLs/IDs as plain text; JSON.parse alone is never trusted). **Identity is bound by workflowId**: an ID seen around a submission binds to that task; a media URL arriving with that ID is that task's video — the strongest identity the app has ever had (stronger than tile fingerprints). Fallbacks, fenced as ever: tile `currentSrc` cross-match (the URL was seen on the network AND sits on the task's own tile), then submission order — only for the task at the front of the queue, only at download time, never a URL first seen before that task was submitted (old projects' links can never be stolen). Unmatched URLs stay *unclaimed* — a wrong video is never delivered. The moment a URL binds, the engine **fetches it immediately** (in parallel with render monitoring — signed FIFE links expire), through the authenticated path (the page session's cookies + Node fetch, saved via the same ffprobe-verified save as always). Capture detaches cleanly with every browser session; cookie values are never logged; signed URLs themselves are never printed (host name only).
2. **Orchestration — backend first, UI last.** `downloadTaskMedia` now runs: **(1) backend-fetch** (bound link, or the in-flight immediate fetch's result), **(2) tile-src / captured-stream** (with the currentSrc cross-match promoting a network-confirmed URL to backend-fetch), **(3) backend order-claim**, **(4) the native UI forms** — and the check-only **download-retry tries the backend first** too. If a whole run sees no media URL on the network at all, the log says so plainly, once — *"Backend par koi video link nahi dikha — UI wale raaste try ho rahe hain"* — silence is the one thing this app no longer does. A pool Activity entry (**Backend download**, stage `download`) records each backend fetch with its identity route.
3. **UI strategies cut to the two that actually exist (inspection part 2, verified in a signed-in project).** A tile's **hover has NO download button** (only Favorite, Reuse prompt, More options) — the hover strategy is **deleted**; it could never have worked. A tile's **⋮ menu** contains exactly **"Download"** — the menu matcher is now that exact label. **"Download media" exists only in the editor view's top bar** — the editor strategy opens the tile, waits for the top bar, and presses exactly that; the editor's ⋮ menu has no download and is no longer searched, and the editor's player is a `<canvas class="video-canvas">`, not a `<video>` — one more reason DOM scraping lost to the backend. All v2.7.0 protections stand unchanged: a download-stage failure still never resubmits, never failovers, never double-charges (backend fetch failures are download-stage too).

## What's new in v2.3.0 — smart tag parser, tag-named downloads, sequence integrity

The owner's bulk workflow pastes prompt lists in many tag styles and joins the downloaded scenes in order — so one missed or mis-named scene silently breaks the whole sequence. 1. **Smart bulk parser (Generate → ✨ Auto, the new default).** Paste in ANY of the owner's styles and Auto detects the marker family itself: `scene1` / `Scene 1` / `SCENE 01` labels, `prompt1` / `Prompt 2` / `PROMPT #1` labels, `1` / `1.` / `1)` / `1:` numbers (including a number alone on its own line), `#1` / `#01` hash tags, and `#00-01` range-style scene tags. Rules are strict about safety: a marker counts **only at the start of a line** — numbers and hashtags inside a prompt (dialogue like "mera #1 kaam", "5 minute baad…") never split it (bare numbers additionally need an ascending sequence before they count as markers). 2. **Downloads are named by tag — and never duplicated away.** Default file name = the prompt's tag, sanitised (`#00-01` → `00-01.mp4`, `scene3` → `scene3.mp4`); a task without a usable tag falls back to `sceneNNN`. 4. **Where the tag lives.** Tags are stored on the task rows (`queue_tasks.prompt_tag`), flow through the pool into the engine (which names the download), survive Resume (check-only recovery keeps them) and per-task Retry — a retried scene lands under the same tag name it should have had. ## What's new in v2.1.0 — the owner's PC-test fixes

**Errors found in the deep analysis and fixed:**
1. **Renderer buttons could stick forever** — Verify All and Import All restored their label only on the success path; a rejected IPC call left them disabled on "Verifying…/Importing…" until restart, and Add/Remove/Clear-History failures were silent unhandled rejections. All of these handlers now use try/catch/finally and show the error.
2. **Shutdown could lose the last changes** — the final database flush sat at the end of an `async` before-quit handler, which Electron does not wait for. The flush is now the first, synchronous step of shutdown.
3. **Silent main-process failures** — there was no `unhandledRejection`/`uncaughtException` logging in the main process; both are now logged instead of vanishing.
4. **Raw system errors on a bad output folder** — creating the download folder threw out of the Start/Retry/Resume IPC handlers; it now returns the app's friendly error message.
5. **Wrong progress row could light up on Resume** — engine "video started" events were mapped to tasks by prompt index alone; a multi-batch resume can contain duplicate indices. The pool now prefers the submitting worker's own current task.
6. **Download poll race** — a file disappearing between the folder scan and its stat call threw out of the native-download poll and failed a healthy task; the poll now treats that as "not ready yet" and keeps waiting.
7. **Misleading crash path in the studio opener** — a few log lines used the account name unguarded; they now fall back to a generic label instead of throwing a TypeError that masqueraded as a Flow-open failure.
8. **Silent blank window on a boot error** — the renderer's init had no error handling; a failed first load now shows a visible message instead of an empty app.

Also verified during the audit and found NOT to be bugs (left unchanged): the sql.js history `LIMIT` binding (SQLite coerces the value correctly), and the many empty `catch {}` blocks in the engine — each is a documented best-effort cleanup (browser close, lock cleanup, dialog dismissal), not hidden error swallowing.

## What's new in v1.8.0 — the ZDola-logic edition

ZDola Studio's multi-account operating logic, adapted to Google Flow (accounts here are Chrome **profiles**, not cookie files — Google's device-bound sessions reject cookie imports, verified in v1.2 testing):

1. **Verify All Accounts** (was "Sync All Credits") — a real health pass, ZDola-style: bounded-concurrency live checks (3 at a time), a classified summary (live / low credits / exhausted / need login / unconfirmed / unknown), and every account a check *could not confirm* is retried once automatically.
2. **Two-strike sign-out** — one `accounts.google.com` redirect no longer declares an account dead. The first observation marks it **Unconfirmed** (balance untouched); only a second explicit sign-out within 24 h confirms **Need Login**. Any live read clears the strikes.
3. **Timed account rest** — Google "unusual activity" now parks the account for a real duration that escalates on repeats (**30 min → 2 h → 12 h**), shown on the card as "Resting till …". Rotation skips resting accounts and lets them back automatically when the rest expires.
4. **Queue survives restarts + check-only recovery** — pending prompts are no longer stranded when the app closes. The Generate tab offers **Resume Queue**; prompts that were mid-flight at close are first looked up **in the Flow project itself** and downloaded if their video exists (no second credit charge, ever), and are only failed — with the reason written on the task — when no matching video can be found.
5. **Usage counts** — ZDola-style counts only (no prompts, no file names): the History header shows videos saved all-time / last 7 days / today, and the counts survive Clear History.

Not ported, deliberately: ZDola's signed auto-update channel (needs a release key + feed owned by the developer) and its cookie-file account method (proven dead end for Google — see above).

## What was fixed vs V2 (audit)

1. **Worker crashes** — V2's worker error handler referenced an out-of-scope variable and could kill the whole queue, leaving tasks stuck in "running". Lite scopes the current task at worker level, fails only that task, and closes its browser cleanly. Leftover "running" tasks are recovered on boot — since v1.8 as pending + verified-in-Flow (see above), not auto-failed.
2. **Balance zeroing** — V2 zeroed real balances in several paths. Lite zeroes only on an explicit live read of 0 or Flow's exhaustion banner; "not enough for this model" is **LowCredits** with the balance intact, and estimated charges never write 0.
3. **Ambiguous sync ≠ logout** — an inconclusive credit check changes nothing; only an explicit `accounts.google.com` redirect sets **Need Login**, and the balance is preserved even then.
4. **Single credit writer** — all credit/status writes go through `engine/creditService.js` as targeted single-row SQL updates from fresh reads. The `accounts.json` mirror is gone; SQLite is the only store, persisted with a 2-second debounce (and flushed on shutdown) instead of a full DB rewrite per mutation.
5. **Settings after rotation** — the engine's settings-configured flag is reset on every browser close/launch, so model/duration/aspect are re-applied for every new account session.
6. **Download identity** — no "latest URL" or "newest tile" fallbacks. A task completes only with its own claimed tile's media; otherwise it fails with a clear reason.
7. **Profile locks** — stale lock *files* are removed, but Chrome processes are **never** killed. A genuinely busy profile is reported and skipped for that run.
